## Decision and scientific limits

Use the two accepted LEAD-POLICY-16 whole recipes, PATCH and RETHINK. A valid public checkpoint supplies exactly two Boolean features: `has_payload_failure` and `has_incomplete`, calculated by the accepted renderer. The four ordered cells are `00,01,10,11`. Neither hidden grades, root/family identity, branch outcomes, task answer keys nor later public checks are deployment features. Public status is not asserted to be causally sufficient: policy value may be evaluated directly without identifying every full-history conditional effect.

Fit a conditional empirical-success rule over all 16 deterministic maps from these four cells to the two actions. Fit its fixed comparator over the two constant maps using the **same** data, family/root weights, score and deterministic tie rule. Conditional versus unconditional empirical success is classical statistical treatment choice, not our invention: [Manski (2004), Econometrica 72, 1221–1246](https://doi.org/10.1111/j.1468-0262.2004.00530.x). What is specialized here is the supported prompt bank, public-status representation, complete-branch bookkeeping and bounded missing-score treatment.

The fixed comparator is development-selected within this declared two-recipe bank. This does not certify broad prompt competence or competitiveness against a strong unrestricted baseline. B2-1R remains the separately specified practical comparator. A negative result for this learner is not evidence that all history representations, free-form prompting or multiround policies fail. A positive result is still one-landmark evidence, not repeated-deployment benefit. Report whether the final mapping is constant; a learned constant cannot establish benefit from personalization.

## Exact supplied-data contract

Implement a pure in-memory API, with an explicit `source_only: true` and `collection_enabled: false` config. No file discovery, historical-outcome loading, fitting on E11/E12/E13, receiver dispatch, network or candidate execution. Supplied toy fixtures only in MRL-28. A future adapter must bind all inputs to a separately committed development manifest; the API cannot establish family independence or provenance by accepting identifiers.

The top-level input has exactly `partition`, `replicates`, `families`. `partition` must equal `development`; `replicates` is a positive integer, with Boolean rejected. `families` is a nonempty list of exact `{family_id, roots}` objects, with unique nonempty UTF-8 IDs and nonempty root lists. Every root ID is unique globally. Sort identifiers canonically for deterministic output, but never use their contents to choose an action.

An actionable root has exactly `root_id`, `state`, `outcomes`; `state` has exactly the two named Boolean features, and `outcomes` has exactly PATCH and RETHINK, each a list of the declared replicate length. Each slot is integer 0, integer 1, or null; reject Boolean, NaN, infinity, fractional scores and unknown fields/actions. Null denotes an unobserved assigned score, never a recorded zero or a dropped/replaced slot. Replicate IDs are the fixed list positions. The future data adapter must check the original assignment ledger; matching list length alone cannot prove that ledger was honored.

A nonactionable planned root has exactly `root_id`, `state: null`, `common_outcome`, `invalid_disposition`. `common_outcome` is 0, 1 or null; the disposition is a nonempty UTF-8 string. It records a common policy-independent outcome before any prompt choice and retains its family/root weight. This is **not** an endpoint adjudication: use null until an independently frozen endpoint and common invalid-checkpoint handling law justify a known score. The source learner neither sends a message nor implements STOP/fallback. A later trial must define and validate that common path and distinguish service failure, missing grade, integrity breach and absorbing STOP. If the policies do not have the same invalid-checkpoint law, this input representation is invalid for that trial.

The roster must include every planned development root, including nonactionable roots and all missing slots. Never reduce the denominator to observed scores or eligible roots. The source API validates internal completeness only; external planned-roster reconciliation remains a release gate. Unknown partitions/fields, empty families, duplicate IDs, malformed types and invalid UTF-8 must fail explicitly before fitting.

## Weights, missing scores and optimization

For G supplied development families and m_g planned roots per family, set w_gi = 1/(G m_g). Within each actionable root and action, let L_gia be the sum of observed binary successes divided by the **planned** replicate count R. Let U_gia = L_gia + missing_gia/R. Thus null contributes [0,1], with all assigned slots retained. For a common root use [y,y] when observed and [0,1] when missing. Preserve those intervals and missing counts in the fit report; do not relabel L as an observed success rate.

For a map pi define the empirical lower-score criterion J(pi) = sum_gi w_gi L_gi,pi(state), adding the common-root lower scores identically for every map. Compute these rational quantities exactly (Python Fraction is adequate), serialize numerators/denominators, and use exact comparisons without numerical tie tolerances.

1. Select b1 = RETHINK iff J(constant RETHINK) > J(constant PATCH); otherwise PATCH. This is a quality-criterion tie rule, not a claim PATCH is cheaper. All deployment costs still require measurement.
2. For each cell s, compare sum over roots in s of w_gi L_gia. Choose the strictly larger action; on equality choose b1. In an unseen cell both sums are zero, so choose b1. This defines d. Do not invent a minimum cell size or tune a threshold from observed labels.
3. Return all four choices, b1, exact lower/upper empirical values for d and b1, per-cell distinct-family counts and weights, missing-slot counts, and whether d is constant. Counts are descriptive support diagnostics, not independent sample sizes for each arm.

Under this finite supplied-data contract, the criterion separates by cell, so the map above maximizes J over the 16 maps and J(d) >= J(b1). This is a deterministic algebraic property, **not evidence of policy improvement**, an unbiased estimate of selected-policy value, a confidence bound, or an assertion of overlap in another population. With complete scores it is ordinary empirical success. With missing scores it maximizes the worst completion of the supplied empirical outcomes over the rectangular [0,1] missing-score set. That conservative training criterion can prefer better observation rates; it does not assume missing-at-random or turn missing data into measured failures. A future endpoint may constrain missing scores more tightly, but that would require a new version rather than silently changing this rule.

Use all declared development families for the final fit. There are no hyperparameters, tuning split or outcome-dependent acceptance threshold in this version. The final d may equal b1. The untouched evaluation remains untouched regardless. Freeze this algorithm before collecting its development outcomes; freeze the fitted mapping, b1 and manifest before evaluation outcomes. If the lead changes the class after examining development results, record a new development version and retain the old result; never tune on evaluation families.

The prediction artifact contains only version, source/config identities, the four-cell map and b1. `predict` accepts exactly the two Boolean public features and the strict validated artifact, with no labels/IDs. Training records and diagnostics are a separate report. For `state: null`, return an explicit nonactionable disposition through a separate API if provided, not a prompt action and not inferred PASS. A future collector must calculate features from the accepted bound public renderer rather than trusting arbitrary caller flags.
